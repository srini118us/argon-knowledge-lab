# ADR-019: Migrate the event bus to Apache Kafka

## Status

Accepted. This record supersedes ADR-003 ("Use RabbitMQ as the event bus"). ADR-003 should be read only for historical context from this point on.

## Context

When ADR-003 was written, the Orion order management platform was a much smaller system. A handful of services needed to tell each other that something had happened, and RabbitMQ gave us a simple, well understood way to do that. The team already knew how to run it, the client libraries were mature, and the routing model (exchanges, bindings, queues) mapped nicely onto the small number of integrations we had at the time. ADR-003 explicitly considered Apache Kafka and set it aside because nobody on the team had operated it in production. That was a reasonable call then.

A lot has changed since. The number of services publishing and consuming events has grown, and the way we use events has changed even more than the volume has. A few patterns keep coming up in design reviews and incident reviews:

- **Replay.** Several consumers need to re-read events after the fact. Today that means asking the producing team to re-publish, writing one-off scripts, or reconstructing state from database snapshots. None of those are good options at two in the morning.
- **Multiple independent consumers.** More and more teams want to read the same stream of order events for their own purposes. With RabbitMQ every new consumer means another queue and another binding, and each queue holds its own copy of the backlog. Fan-out works, but it is fiddly and it grows operational surface area with every new subscriber.
- **Ordering.** Consumers that care about the lifecycle of a single order want to see events for that order in the order they happened. We have achieved this in places with careful queue design and single consumers, which caps throughput and makes scaling awkward.
- **Slow consumers.** When a downstream consumer slows down, messages pile up in the broker and broker health becomes the incident.

We also now have engineers across several teams who have run Kafka elsewhere, and the Platform team has built up the experience that was missing when ADR-003 was decided. The main reason for rejecting Kafka last time no longer holds.

## Decision

We will migrate the Orion event bus from RabbitMQ to Apache Kafka.

Kafka becomes the standard transport for asynchronous, event driven communication between Orion services. New event streams are created in Kafka from the date of this ADR. Existing RabbitMQ flows are moved over in phases (see Migration approach below) and RabbitMQ is retired once the last flow is moved.

### Topic conventions

- Topics are named after the business stream they carry, in lower case with hyphens, for example `order-events`.
- Each topic has a single owning service that is the only producer. Consumers are free to subscribe without asking the producer to change anything, but they must register themselves with the platform so we know who depends on what.
- Events for a single business entity are keyed by that entity's identifier so that all events for, say, one order land on the same partition and are read in order.

### The order-events topic

The `order-events` topic is created with **24 partitions**. This is the first topic we are standing up and the one with the most consumers, so it got the most discussion.

The partition count was chosen to give consumer groups enough room to scale horizontally as order volume grows, without needing to repartition early. Repartitioning a keyed topic breaks the per key ordering guarantee for in flight data, so we would rather pick a number with headroom now than revisit it under pressure. Consumer groups for `order-events` can run as many active instances as there are partitions; any instances beyond that sit idle as warm standbys.

### Retention

Topic retention follows the default defined in POL-DR-02 unless an ADR overrides it for a specific topic. This ADR does not set any topic specific retention. If a team needs longer or shorter retention for a particular topic, that is a separate decision recorded in its own ADR with the reasoning written down, so that retention does not drift topic by topic through ad hoc configuration changes.

## Alternatives considered

**Stay on RabbitMQ and invest in tooling.** We could build replay tooling and better fan-out automation on top of RabbitMQ. We decided against it because we would be rebuilding, badly, features that Kafka provides as part of its core model. The ordering and slow consumer problems would also remain.

**RabbitMQ streams.** Newer RabbitMQ releases offer a stream data structure with log semantics. It was a serious candidate because it would have let us keep one broker technology. In the end the ecosystem around Kafka (connectors, client support across our languages, operational tooling, and the experience people already bring to the team) tipped the decision.

## Consequences

### Positive

- Consumers can replay from any point still within retention, which simplifies recovery after downstream bugs and lets new consumers bootstrap from history.
- New consumers can be added without changes to the producer or the broker topology.
- Per entity ordering becomes a property of the platform rather than something each team has to engineer.
- Slow consumers lag rather than threaten broker health. Lag becomes a metric we alert on instead of a capacity incident.

### Negative

- Kafka is more complex to operate than our RabbitMQ setup. The Platform team takes on cluster operations, upgrades and capacity planning.
- Consumers become responsible for tracking their own offsets and handling at least once delivery correctly. Every consumer must be idempotent. This was always good practice, but it is now mandatory.
- Some RabbitMQ patterns, such as per message routing keys with complex bindings and per message TTLs, have no direct equivalent. Flows that rely on them need redesign rather than a straight port.
- For a period we run two event buses side by side, which adds load for on-call.

## Migration approach

1. **Stand up Kafka and `order-events` first.** order-service begins dual publishing: events go to both RabbitMQ and Kafka. Existing RabbitMQ consumers are untouched.
2. **Move consumers one at a time.** Each consuming team switches to the Kafka topic, runs in shadow mode where practical, compares results, and then cuts over. Teams own their own cutover, with the Platform team on hand to help.
3. **Stop dual publishing** for a stream once every known consumer of it has moved.
4. **Repeat for remaining streams**, then decommission RabbitMQ.

The rule for each stream is simple: we do not stop publishing to RabbitMQ until we have positive confirmation that nobody is still reading from it.
