# ADR-011: Service to service authentication

| Field | Value |
|---|---|
| Document ID | ADR-011 |
| Version | v1 |
| Title | Service to service authentication |
| Date | 2025-01-20 |
| Status | Accepted |

## Context

Orion has grown from a handful of services that trusted each other implicitly into a platform where a dozen services call one another constantly. Until now, internal authentication has been inconsistent. Some services checked a shared static token passed in a header, some relied on the assumption that anything reaching them over the internal network must be legitimate, and a few had no check at all.

That drift has become a real problem for three reasons.

First, we cannot answer a simple audit question: "which service called this endpoint, and was it allowed to?" Static shared tokens identify nothing. If the token leaks, every caller looks the same, and revoking it breaks every caller at once.

Second, authorization decisions are scattered. When order-service was given access to a pricing-service endpoint last year, the change involved editing a hard coded allow list inside pricing-service, which then had to be deployed.

Third, onboarding a new service is slow and error prone. The new service has to discover which mechanism each downstream dependency expects and implement all of them.

We already run identity-service, which issues tokens for end users and administrative tools. Extending it to cover machine identities is a natural step.

## Decision

**All service to service calls inside Orion use OAuth2 client credentials issued by identity-service.**

In practice this means:

- Every Orion service is registered in identity-service as an OAuth2 client with its own client identity.
- Before calling another service, the caller obtains an access token from identity-service using the client credentials grant and presents it as a bearer token on the request.
- The receiving service validates the token (signature, issuer, audience and expiry) and checks that the calling client holds the scope required for the endpoint being invoked.
- Scopes are defined by the receiving service and granted to callers through identity-service configuration, not through code changes in the receiving service.

**This applies to every internal call, including payment-service calling inventory-service.** There are no exemptions for "trusted" or "low risk" paths. We specifically call out payment-service calling inventory-service because it was the example most often raised during review as a candidate for an exception, on the grounds that both services sit in the same part of the platform and the call is read heavy. The answer is no: the rule is uniform so that nobody has to remember which calls are special.

**Transport level security requirements for these calls are defined in POL-SEC-01 and are not repeated here.** This ADR is about caller identity and authorization at the application layer. How the connection itself is protected is a policy matter owned by POL-SEC-01, and keeping it there means the two can evolve independently without one document silently contradicting the other.

## Rationale

We considered three options.

**Option A: keep shared static tokens, but give each caller its own token.** This would fix the identification problem cheaply. It does nothing for central authorization, rotation is still manual, and it means building and running a second credential system alongside identity-service.

**Option B: rely on network placement.** Restrict which services can reach which others using network rules and treat reachability as authorization. This is attractive because it needs no application changes, but it couples security to infrastructure layout, gives no per request identity in logs, and offers nothing at the endpoint level.

**Option C: OAuth2 client credentials via identity-service.** This gives every caller a distinct identity, puts authorization grants in one place, produces short lived tokens rather than long lived secrets on the wire, and reuses a system we already operate. The cost is an additional token fetch, which client libraries mitigate by caching tokens until shortly before expiry.

We chose Option C. Network controls remain useful as defence in depth, but they are not the authorization mechanism.

## Consequences

**Positive**

- Every inbound request can be attributed to a named calling service, which makes audit logs meaningful.
- Granting or revoking access becomes a configuration change in identity-service, reviewable in one place.
- New services follow a single, documented pattern.

**Negative**

- identity-service becomes a hard dependency for internal traffic. If it is unavailable and cached tokens expire, calls start failing. identity-service's maintainers must treat its availability accordingly, and client libraries must cache tokens and refresh them ahead of expiry rather than on every call.
- Every service needs a code change to adopt the shared client library.
- Debugging becomes slightly harder: a failed call may now be an authorization failure rather than a functional one. Services must log rejected tokens with enough context (caller, required scope, reason) to make this obvious.

## Implementation notes

- A shared client library will handle token acquisition, caching and refresh, and a shared middleware will handle validation and scope checks on the receiving side. Teams should not hand roll either.
- Client secrets for registered services are stored and rotated according to POL-SEC-01. They must never be committed to repositories or baked into images.
- During migration, a receiving service may temporarily accept both the legacy mechanism and the new token, but must log every legacy call so remaining callers can be found and chased. The dual mode is removed once logs show no legacy traffic.
