# RFC-008: GraphQL gateway for Orion

```
Document ID:  RFC-008
Version:      v1
Title:        GraphQL gateway for Orion
Date:         2025-04-22
Status:       Withdrawn
```

---

## Status: Withdrawn

**This RFC is withdrawn.** It proposed a GraphQL gateway in front of Orion APIs. It was withdrawn because the API team prioritized the Order API v2 migration. The proposal is preserved here so that the reasoning is not lost if the idea comes back. Nothing in this document is planned work.

---

## 1. Problem

Clients of the Orion order management platform increasingly need data from several services to render a single screen or complete a single task. A typical order detail page, for example, needs the order itself, current shipment and tracking information, payment status, any returns in progress and some customer details. Today each client fetches this by calling several APIs in turn and stitching the results together.

This creates a few recurring problems:

- **Chatty clients.** Rendering one view means many round trips. Mobile and partner clients feel this most.
- **Over fetching.** Each REST endpoint returns its full resource whether the client needs one field or all of them.
- **Duplicated aggregation logic.** Every client team writes and maintains its own version of the stitching code, and those versions drift apart. When an underlying API changes, several clients break in slightly different ways.
- **Inconsistent conventions.** Error shapes, pagination and naming differ across services, so clients carry a lot of service specific handling.

## 2. Proposal

Introduce a GraphQL gateway as a single entry point in front of Orion APIs.

- The gateway exposes one GraphQL schema describing orders, shipments, payments, returns and related customer data as a connected graph.
- Each field in the schema is resolved by calling the existing service API that owns that data. Services themselves do not change their APIs and do not need to know GraphQL.
- Clients request exactly the fields they need in a single query, and the gateway fetches from the relevant services and assembles the response.
- Authentication is handled at the gateway for external clients, and the gateway calls downstream services using its own service identity in line with ADR-011.

### 2.1 What the gateway would not do

- It would not contain business logic. It aggregates and reshapes; it does not decide.
- It would not replace service APIs. Services keep their existing interfaces, and internal service to service calls would continue to go direct.
- It would not handle writes in the first phase. Mutations were deliberately out of scope until read use cases were proven.

## 3. Rollout sketch

1. Build a read only schema for the order detail use case, as a proof of concept.
2. Migrate one client screen to use the gateway and compare performance and complexity with the existing approach.
3. If successful, expand the schema to additional read use cases.
4. Revisit writes in a separate RFC.

## 4. Alternatives considered

**Backend for frontend services.** One aggregation service per client type. Simpler to reason about than a general graph, but it multiplies the number of services to maintain and does not solve the duplication problem across clients of the same type.

**Composite REST endpoints.** Add aggregate endpoints to existing services, for example an "order with everything" endpoint on order-service. Quick to deliver, but it pushes knowledge of other services' data into order-service and couples them more tightly.

**Do nothing.** Accept the client side cost. Viable in the short term, but the duplication grows with every new client.

## 5. Risks and open questions

- **Performance.** Naive resolvers can generate many downstream calls per query. Batching and caching at the gateway would be needed from the start.
- **Ownership.** A shared schema needs a clear owner and a contribution process, or it becomes everyone's problem and nobody's job.
- **Authorization at field level.** Some fields are sensitive. The gateway would need to respect the authorization rules of each underlying service without re implementing them.
- **Versioning.** GraphQL encourages evolving a single schema rather than versioning endpoints. That fits poorly with services that still expose versioned REST APIs, and the interaction needed more thought.
- **Operational load.** The gateway would sit on the critical path for many client requests, so its own reliability becomes important.

## 6. Discussion summary

Review comments were broadly positive about the problem statement. Most reviewers agreed the client side duplication is real and getting worse. Reaction to the solution was more mixed: several reviewers liked GraphQL for this use case, while others felt that cleaning up the underlying APIs should come first, because a gateway over inconsistent APIs would inherit their inconsistencies.

That second point turned out to be decisive in practice. The API team concluded that its capacity was better spent on the Order API v2 migration, which addresses several of the underlying API problems directly and has a hard external driver in the retirement of Order API v1. Running both efforts in parallel would have stretched the same people across two large pieces of work.

## 7. Withdrawal

The author withdrew this RFC after the API team prioritized the Order API v2 migration. The withdrawal is not a rejection of the idea. If it is revisited, a new RFC should:

- Re examine the problem in light of whatever Order API v2 has fixed.
- Address the ownership and field level authorization questions above before proposing an implementation.
- Reference this RFC rather than starting from scratch.
