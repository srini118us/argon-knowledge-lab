# ADR-003: Use RabbitMQ as the event bus

> **Status: Superseded by ADR-019.** This record is kept for historical context. Do not use it as guidance for new work. Read ADR-019 for the current event bus decision.

## Context

The Orion order management platform at Northwind Logistics has grown from a small set of services that called each other directly into a larger estate where many services need to know when something happens elsewhere. Today, when a downstream service needs to react to a change, the upstream service either calls it directly or the downstream service polls. Both patterns are causing pain:

- Direct calls create tight coupling. Adding a new consumer means changing the producer, redeploying it, and coordinating releases across teams.
- Polling wastes capacity, adds latency, and produces subtle bugs when two pollers race over the same rows.
- Failures cascade. When a consumer is slow or down, the producer either blocks or has to build its own retry logic, and every team has built that logic slightly differently.

We want a shared asynchronous messaging layer so that services can publish facts about what happened and let interested consumers subscribe, without the producer knowing who is listening. This is the first platform level decision on messaging for Orion, so it sets conventions that many teams will build on.

## Decision drivers

1. **Operational familiarity.** Whatever we pick, the Platform on-call rotation has to run it at three in the morning. A system we understand beats a system that is theoretically better but that nobody can debug.
2. **Delivery semantics.** Consumers need acknowledgements, redelivery on failure, and dead lettering for poison messages.
3. **Routing flexibility.** Several consumers want only a subset of messages. We would like routing to be a broker concern rather than filtering in every consumer.
4. **Client library maturity** across the languages used by Orion teams.
5. **Time to value.** Teams are waiting on this to decouple work already on their roadmaps.

## Considered options

### Option A: RabbitMQ

A mature message broker with exchanges, queues and flexible routing (direct, topic and fanout exchanges). Supports per message acknowledgement, dead letter exchanges and a management UI that the team already knows from earlier internal tooling.

- Pros: the team has run it before; routing model fits our "publish once, route to interested consumers" need; good client libraries; dead lettering is built in; quick to stand up.
- Cons: messages are generally removed once consumed, so replaying history for a new consumer or after a bug is awkward; scaling very high throughput needs careful queue design.

### Option B: Apache Kafka

A distributed, partitioned commit log. Consumers track their own offsets and can replay retained history.

- Pros: replay of past events; strong ordering per partition; widely adopted for event streaming at scale; a natural fit if we later want event sourcing or analytics streams.
- Cons: **the team lacked operational experience with Kafka at the time of this decision.** Nobody on the Platform rotation had run it in production, tuned it, or recovered it from a failure. The operational model (partitions, consumer groups, offset management, rebalancing) is a significant learning curve, and getting it wrong in production would put order flow at risk.

## Decision

**Adopt RabbitMQ as the Orion event bus.**

Apache Kafka was seriously considered and in several respects is the stronger long term technology, particularly for replay. It was rejected at this time because the team lacked operational experience running it. We judged the risk of operating an unfamiliar distributed log underneath order flow to be greater than the cost of RabbitMQ's limitations for our current needs.

## Conventions that follow from this decision

- Producers publish to named exchanges, one per business domain, rather than directly to queues.
- Each consuming service owns its own queue(s) and bindings. Producers do not create consumer queues.
- Every consumer queue has a dead letter exchange configured. Messages that repeatedly fail land there for inspection rather than looping forever.
- Message payloads are versioned JSON with an explicit schema version field. Consumers must ignore unknown fields.
- Consumers must be idempotent. Redelivery is expected, not exceptional.
- Publishing is fire and forget from the producer's point of view; a producer must not wait on a consumer's processing.

## Consequences

**Positive**

- Services can be decoupled incrementally. Teams can move one integration at a time from direct calls to published messages.
- The Platform rotation can support the bus from day one with existing knowledge and runbooks.
- Dead lettering gives us a consistent place to look when messages fail, which should cut down the bespoke retry code scattered across services.

**Negative**

- There is no general replay. If a consumer has a bug and drops or mishandles messages, recovering requires the producer to republish or a manual reconstruction from source systems. We accept this for now.
- New consumers cannot bootstrap from history. They will need a backfill from the owning service's data store.
- If our needs move toward event streaming, analytics feeds or replayable history, this decision will need to be revisited.

## Revisit triggers

We agreed to reopen this decision if any of the following happens:

- Replay becomes a recurring operational need rather than an occasional inconvenience.
- The team builds enough Kafka experience (through training, hiring, or other internal use) that the main reason for rejecting it no longer holds.
- Throughput or fan out requirements outgrow comfortable RabbitMQ queue design.

## Notes

A few people in the review pushed hard for Kafka. The consensus was "right tool eventually, wrong time now". See ADR-019 for how that played out.
