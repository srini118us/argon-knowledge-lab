# ADR-007: Order API versioning and idempotency

## Context

The Order API is the front door to the Orion order management platform. Every storefront, partner integration and internal tool that creates an order at Northwind Logistics goes through it, and order-service is the service behind it. The API has been running as Order API v1 since the platform launched, and for most of that time it has done its job well enough that nobody wanted to touch it.

The problem that forced this decision is retries. Clients of the Order API live on networks we do not control. Mobile storefronts drop connections, partner systems sit behind their own gateways with their own timeouts, and our own batch tools retry aggressively when a call does not come back in time. When a client sends an order creation request and the response is lost or arrives late, the client has no way to know whether the order was created. The safe thing from the client's point of view is to send the request again.

On Order API v1 that safe thing is not safe at all. v1 has no way to recognise that a second request is the same logical order as the first. Each request that reaches order-service is treated as a brand new order. **Client retries could create duplicate orders on v1**, and in practice that is what happens: a timed out request that actually succeeded on our side, followed by a retry that also succeeds, leaves two orders where the customer wanted one.

Duplicate orders are expensive in ways that are easy to underestimate. Stock gets reserved twice, the customer may be charged twice, warehouse staff pick and pack goods that nobody wants, and the support team then has to unwind all of it by hand.

We looked at patching v1 in place, but adding a new required element to an existing contract would break every client that does not send it. Making it optional would leave the duplicate problem in place for exactly the clients most likely to cause it. A new version of the API is the honest way to change the contract.

## Decision

1. We will introduce **Order API v2**.
2. **Order API v2 introduces a mandatory Idempotency-Key header on order creation.** A request to create an order without this header is rejected as a client error. The key is chosen by the client and must be unique per logical order the client intends to create.
3. When order-service receives an order creation request with an Idempotency-Key it has already seen from the same client, it does not create a new order. It returns the result of the original request instead, so a retry is indistinguishable from a successful first attempt.
4. **Order API v1 will be deprecated once v2 is available.** Deprecation means v1 stays up for existing clients while they migrate, but no new integration will be onboarded to v1 and no new features will be added to it.
5. The detailed retention window for idempotency keys, rate limits and payload changes belong in the v2 API specification, not in this ADR.

## How clients should generate keys

The header only works if clients use it properly, so the guidance we will publish with v2 is:

- Generate the key once, when the client first decides to create the order, and store it with the client's own record of that order.
- Reuse the same key for every retry of that same order. Never generate a fresh key on retry; that defeats the whole mechanism.
- Use a value that is unique across the client's orders. A random UUID is the expected choice.
- Do not reuse a key for a different order, even after a long time. Behaviour in that case is defined by the v2 specification and clients should not depend on it.

## Alternatives considered

**Server side duplicate detection on v1.** We could try to spot duplicates by comparing order contents (same customer, same items, short time apart). This was rejected. It guesses at intent, and legitimate repeat orders do exist, especially from business customers who reorder the same items. A heuristic that blocks a real order is worse than a duplicate.

**Optional idempotency header on v1.** Cheaper to roll out, but the clients causing duplicates are typically the older, less maintained integrations that would never adopt an optional header. It would let us say we had solved the problem without actually solving it.

## Consequences

Positive:

- Retries become safe for every v2 client. Integrators can use standard retry libraries without worrying about duplicates.
- Support effort spent on unwinding duplicate orders should drop as clients move to v2.
- Having a clean version boundary gives us a place to make other contract improvements that v1 could not absorb.

Negative:

- We run two API versions in parallel for a while. That means two sets of contract tests, two sets of documentation and two code paths in order-service.
- order-service has to store idempotency keys and look them up on every order creation. This is new state that needs to be sized, monitored and included in recovery planning.
- Every existing client has to do migration work. Some partner integrations will move slowly, and we should expect to chase them.
- Until v1 is actually retired, the duplicate order risk is still present for clients that have not moved.

## Follow up

- The API team will publish the Order API v2 specification, including key retention and error behaviour.
- Once v2 is available, the v1 specification will be marked Deprecated, and a sunset date will be agreed and communicated separately.
- Client owning teams should plan their migration as soon as the v2 specification is published rather than waiting for the sunset announcement.
