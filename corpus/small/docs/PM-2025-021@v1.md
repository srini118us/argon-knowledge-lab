# PM-2025-021: Duplicate orders from v1 clients

- **Document ID:** PM-2025-021
- **Version:** v1
- **Title:** Duplicate orders from v1 clients
- **Date:** 2025-10-06
- **Status:** Final
- **Incident date:** 2025-10-02
- **Service affected:** order-service (Order API v1)

This is a blameless postmortem. The goal is to understand how our systems and processes allowed this to happen, not to assign fault to any person or team.

## Summary

On 2025-10-02 a number of customers received duplicate orders. Each duplicate was a complete, valid order that went through the normal order flow. The duplicates came from client integrations that were still calling Order API v1. When some of their create requests timed out, those clients retried, and because v1 has no idempotency mechanism, each retry created a brand new order.

The underlying weakness was known. It is the reason Order API v2 exists, with its mandatory `Idempotency-Key` header, and the reason ADR-007 called for v1 to be deprecated once v2 was available. What we had not done was move the remaining v1 clients off quickly enough.

## Impact

- Customers affected by the duplicates were charged for and, in some cases, shipped more than one order.
- Customer support handled a wave of contacts about duplicate charges and duplicate confirmations.
- Warehouse staff had to identify and intercept duplicate orders that had not yet shipped.
- The finance contacts needed to reconcile refunds for duplicates that were not caught before payment capture.

No data was lost and no orders were missed. The problem was strictly one of extra orders.

## Root cause

Clients still on Order API v1, which has no idempotency, retried timed out requests and created duplicate orders.

Walking it through:

1. order-service became slow for a period. The cause of the slowdown is tracked separately and is not the subject of this postmortem; a slowdown of some kind will always happen eventually.
2. Some v1 create requests took longer than the clients were willing to wait. From the client's point of view, those requests failed.
3. On the server side, many of those requests had in fact succeeded. The orders were created; the response just never made it back in time.
4. The clients' retry logic sent the same order again. v1 has no way to recognise that a request is a repeat of an earlier one, so it treated each retry as a new order and created it.

v2 clients went through the same slowdown and did not produce duplicates. Their retries carried the same `Idempotency-Key` as the original attempt, so the API returned the original order instead of creating a new one. That contrast is the clearest possible evidence that the v2 design works as intended.

## Contributing factors

- **The v1 tail was longer than we thought.** We knew some clients were still on v1, but we did not have a good, current list of who they were or how much traffic they sent. Our migration tracking relied on teams self reporting.
- **The deprecation had no urgency.** v1 was marked deprecated and had a published sunset date, but from the clients' perspective it still worked fine, so the migration kept sliding down their priority lists.
- **Initial misdiagnosis.** Duplicate confirmation emails looked like a notification problem. We spent time on notification-service before confirming the orders themselves were duplicated. A quick query for "same customer, same lines, created close together" would have pointed us at the real issue sooner.
- **Retries are correct behaviour.** The clients did nothing wrong by retrying a timed out request. Retrying is exactly what a well behaved client should do. The flaw is in an API that makes retrying unsafe.

## What went well

- v2 behaved exactly as designed under stress.
- Support raised the alarm early, which kept the window of duplicates shorter than it could have been.
- The fulfillment and finance contacts picked up cleanup quickly and coordinated well with each other.

## What did not go well

- We did not have an at a glance view of v1 traffic by client.
- The first hour of the investigation was spent on the wrong service.
- There was no ready made playbook for "find and reverse duplicate orders", so cleanup involved ad hoc queries.

## Actions

### Primary action: accelerate the v1 sunset

The Order API v1 sunset was accelerated. Clients still on v1 were told to move to v2 before the sunset, and that the sunset will not be pushed back. The API owners contacted each remaining v1 client directly rather than relying on a broadcast announcement, and the revised sunset is now reflected in SPEC-ORDER-API v1.

The reasoning is simple. Every day v1 stays available is another day the same failure can recur. The safety mechanism already exists in v2; the job now is to make sure everyone is using it.

## Lessons

The main lesson is about deprecations, not about idempotency. We already knew how to prevent this, and we had already built the fix. A deprecation without a firm, enforced end date leaves the old behaviour live indefinitely, and the risk it carries stays live with it. When a deprecated version has a known correctness flaw, the sunset should be treated as risk reduction work with real priority, not as housekeeping.
